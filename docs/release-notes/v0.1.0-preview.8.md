# v0.1.0-preview.8

## Summary

Squirix 0.1.0-preview.8 introduces replica sets with synchronous replicated mutations committed on a majority, and
the term, voting, and fencing building blocks for failover. The owner of each key keeps leading its group; this
release does not promote a new leader in a running cluster. RF=1 keeps single-owner behavior with durability per
node, and RF>1 requires explicit opt-in plus persistence and internode mTLS.

Still an early preview — not production-ready. API, wire format, and on-disk layouts may change during 0.x.

## Changes

- **Breaking (client):** every `ISquirixSerializer` method now takes a `JsonTypeInfo<T>` argument (NativeAOT /
  `IsAotCompatible`); custom serializer implementations must add the parameter and register source-generated
  contexts via the new `SquirixClientOptions.JsonSerializerContexts`
- **Breaking (server):** `SquirixErrorCode` drops `BadRequest`, `Conflict`, `InvalidCacheName`, and `NotFound`;
  adds `None` and `CommitOutcomeUnknown` — update exhaustive switches over this enum
- **Breaking (server hosting):** `Configurator.TryValidateSettingsFileAsync` is renamed to
  `ValidateSettingsFileAsync`, `TryLoadFromFileAsync` is removed in favor of `LoadAsync`, and
  `ApplyCommandLineOverrides` takes an additional replication opt-in flag
- Mutations can now throw the new `CommitOutcomeUnknownException` when the durable commit outcome is ambiguous;
  retrying with the same `operation_id` stays idempotent
- Synchronous replicated mutations with majority commit; RF=1 keeps single-owner behavior with no replication or automatic failover
- Explicit replication opt-in for RF>1 (`ReplicationEnabled`, `--enable-replication`); RF>1 startup without it is refused
- Election building blocks: durable `current_term` and log-freshness voting in the group log, with no production caller, so no automatic promotion
- Leader authority and stale-term checks, and a single bounded client reroute on a stale-term answer
- Executable protocol model and tests for failover, partition-safety, and rejoin rules, not active in a running cluster;
  RF=2 stays a synchronous mirror with no promotion after peer loss
- Write-ahead idempotency intent recorded before mutation execution
- Replication metrics and replica readiness on `/metrics` and `/health/ready/details`
- `squirix-server doctor` reports replica status for RF>1 hosts
- RF=3 Docker Compose HA example with persistence and mTLS
- Homogeneous cluster package version enforced through the topology fingerprint; mixed versions fail readiness

## Install

dotnet add package squirix --version 0.1.0-preview.8
dotnet add package squirix.server --version 0.1.0-preview.8
dotnet tool install --global squirix.server.tool --version 0.1.0-preview.8
